# 教授報告逐字講稿｜Mi-V RV32 × 10 通道 CORDIC ln／exp

> 建議 7～8 分鐘，搭配 GitHub README 與截圖。以「我們」口吻撰寫；可直接念。括號為切換畫面的提示，不必唸出。

## 0:00–0:50｜研究動機與目標

教授好，我今天要報告的題目是「**Mi-V RV32 CPU 整合十通道平行 CORDIC，實現 ln 和 exp 運算與效能比較**」。

CORDIC 是一種主要利用**移位、加法、減法和查表**的數值演算法，適合在硬體中實作。這次我們想解決的問題是：如果 CPU 需要連續計算十筆自然對數或指數函數，讓十個硬體核心平行工作，能不能比使用一個硬體核心依序工作更快？而且把 CPU 控制和讀寫資料的時間都算進去之後，還能保留多少效益？

我們的目標不是只看 CORDIC 單元有沒有算對，而是讓**真正的 Mi-V CPU 在 RTL 模擬中執行 SoftConsole 的程式**，並完成資料寫入、啟動、讀回、驗證和效能量測。

## 0:50–1:50｜系統架構

（指向 README 的架構圖）

整個系統從 SoftConsole 開始。我們撰寫 C 語言程式，由 RISC-V 工具鏈編譯成 Intel HEX，再放到 ModelSim 模擬的指令記憶體，起始位址是 `0x60000000`。

Mi-V RV32 CPU 從記憶體取指令，透過 LSU 執行一般的 `lw` 和 `sw` 指令，讀寫我們定義的 MMIO 暫存器。程式先把十筆資料分別寫進十個輸入位置，再對 `0x60010080` 寫入 1，**一次啟動十個 CORDIC 通道**。

CPU 接著讀取 STATUS，確認 DONE；再讀取十筆 ln 或 exp 結果，寫回 RAM。最後 CPU 在 `0x60001040` 寫入成功旗標。ln 用 `0xC0DE100A`，exp 用 `0xC0DE200A`，讓 ModelSim Testbench 可以確定軟體真的執行到成功結束。

這邊要特別說明：我們早期做過自訂 `CORDIC_END` 指令的單步測試；但現在這份**十通道完整 ln／exp 專題使用的是 MMIO 控制介面**。兩者不是同一種整合方式。

## 1:50–2:50｜演算法和數值格式

雙曲 CORDIC 可以處理雙曲函數。我們對 ln 使用 vectoring mode，依據 `ln(a) = 2 × atanh((a−1)/(a+1))`；對 exp 使用 rotation mode，利用 `exp(x) = cosh(x)+sinh(x)`。

硬體採 16 次迭代，其中 shift 4 和 shift 13 會各重複一次，這是雙曲 CORDIC 演算法需要的修正。十通道版本有十組獨立的 X、Y、Z 狀態，因此可以**在同一段 16 週期內處理十筆資料**。

為了降低硬體浮點運算複雜度，我們使用 Q12 定點數。數值 4096 代表 1.0。例如 ln(0.5) 約得到 −2839、ln(2) 約得到 2839；exp(0) 得到 4096、exp(約 0.693) 約得到 8192。這次使用的測試容許誤差是 ±3 個 Q12 單位。第一版 ln 只支援 0.5 到 2.0，exp 輸入約為負 ln2 到正 ln2。

## 2:50–3:50｜我們如何證明整合成功？

（展示兩張 CPU PASS 截圖）

我們先分別驗證 ln、exp 的十通道 RTL，再驗證 MMIO 讀寫、非法輸入、START、DONE。最後才把 SoftConsole 編譯的 HEX 載入真正的 Mi-V CPU Testbench。

在 ModelSim Transcript 裡，可以看到 CPU 確實透過 MMIO 設定十筆輸入，發出一次 START、查詢 STATUS、讀回結果並寫回 RAM。ln 的成功旗標是 `C0DE100A`，exp 是 `C0DE200A`。兩種函數各十筆結果都符合預期，因此完整 CPU 整合測試都 PASS。

這表示**CPU、韌體、MMIO 與 CORDIC 的 RTL 互動已成功**。但是目前仍然是模擬，還不能說已經下載到 FPGA 板子上運作。

## 3:50–5:15｜核心和 CPU 效能比較

（展示核心效能與系統效能表）

接下來是最重要的量化結果。我們建立一個公平的對照組：**只用一個真正的 CORDIC 運算核心，透過排程器依序處理十筆資料**。CPU、SoftConsole 韌體、MMIO 位址和十筆輸入，都跟十核心平行版本相同。

先看不含 CPU 的純核心效能：單核心依序處理十筆 ln 或 exp 都是 **169 週期**；十核心平行處理是 **16 週期**，兩種函數的核心加速比都是 **10.563 倍**。而且逐筆比較十組輸出，結果全部一致。

但是如果加入 CPU 執行程式、MMIO 傳輸、讀回和檢查，效果就不同。ln 的 CPU 端到端週期由 **522 降到 352**，加速比 **1.483 倍**；exp 由 **524 降到 354**，加速比 **1.480 倍**。

也就是說，同樣是十筆資料，十通道系統分別都省了 **170 個 CPU 週期**。在這次 10 ns 的模擬時脈下，相當於節省 1.7 微秒。

## 5:15–6:10｜為什麼系統只有 1.48 倍？

核心能快十倍，但整個 CPU 系統約只有 1.48 倍，主要是因為**只有運算階段被平行化**。CPU 還是需要一筆一筆寫入十個輸入、輪詢 STATUS、讀回十個結果、在軟體做比較，然後寫入 RAM。

以 ln 為例，十通道核心 BUSY 只有 **16 週期**，但從核心完成到 RAM 成功旗標，還有 **258 週期**。因此整體效能除了取決於硬體計算速度，也取決於 CPU 的控制和資料搬移成本。

這一點是我們專題很重要的結論：**硬體平行化有明確效益，但系統加速比不能直接拿核心加速比替代。**

## 6:10–7:00｜成果、限制及後續研究

最後整理成果：目前我們已完成十通道完整 ln／exp 的 RTL 功能驗證、MMIO、SoftConsole 韌體到 Mi-V CPU 的整合，以及單通道和十通道的核心與 CPU 系統效能比較。

目前的限制是尚未做到 Libero 綜合後的 LUT、FF、Fmax 和 FPGA 實機測試，也還沒完成大輸入範圍的 range reduction。因此我們不會把這些模擬結果說成實機最高速度。

後續如果要提升系統效能，可以減少 CPU 對資料搬移和輪詢的負擔，例如改善批次介面或採用其他資料搬運方式。下一步也可以透過 Libero 的資源及時序報告，比較十核心增加多少硬體成本、是否值得換取目前約 1.48 倍的端到端加速。

以上是我們目前的成果，謝謝教授。

## 教授可能會問的問題（建議回答）

**Q1：為什麼 10 通道核心是 10.563 倍，但 CPU 系統只有 1.48 倍？**  
A：因為核心的 16 次 CORDIC 迭代可以十筆同時做，但 CPU 寫入、輪詢、讀回和軟體比對仍需要週期。從核心 DONE 到完成旗標約 258 週期，是目前的主要系統負擔之一。

**Q2：169 / 16 怎麼可能超過十倍？**  
A：分母是十通道一次批次的 16 週期；分子是單通道連續完成十筆、包含批次啟動間隔的 169 週期。這是**處理十筆資料的吞吐量比較**，不是單筆運算延遲提高十倍。

**Q3：為什麼要用 Q12？精度夠嗎？**  
A：定點數便於在 RTL 中實現移位和加減。4096 代表 1.0；目前功能測試採 ±3 個 Q12 LSB 的容許誤差，驗證向量全部通過。但仍需完整範圍與極端值測試，才能宣稱一般用途精度。

**Q4：CPU 是真的在跑程式，還是 Testbench 幫你算好？**  
A：Testbench 載入 SoftConsole 編譯的 HEX，由真實 Mi-V RV32 RTL 模組取指令及執行，LSU 進行 MMIO 記憶體存取。Testbench 只負責模擬記憶體／匯流排與檢查輸出，不是取代 CPU 直接產生結果。

**Q5：你們是使用自訂 RISC-V 指令嗎？**  
A：早期驗證過 `CORDIC_END` 單步自訂指令。這次十通道完整 ln／exp 由 CPU 使用一般記憶體讀寫指令透過 MMIO 控制，不能混為一談。

**Q6：你們有做 FPGA 實作和 LUT／Fmax 比較嗎？**  
A：目前還沒有。此階段是 ModelSim RTL 功能和固定模擬時脈的週期評估。綜合後資源、時序和實機量測會是後續工作。

**Q7：單通道的比較公平嗎？**  
A：單通道對照組是**真正一個核心＋十筆依序排程器**，與十通道使用同一版 CPU 韌體與 MMIO 批次 API。因此比較的是平行硬體對同一 CPU 控制流程的影響，不是兩種不同軟體 API 的比較。
